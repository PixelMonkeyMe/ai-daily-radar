进入 QA（质量保证）模式。

用户输入: $ARGUMENTS

## 前置：获取测试输入
QA 不自己猜要测什么，而是从以下来源获取：
1. **PRD 验收标准** → 每一项都必须有对应的验证
2. **Dev 交接清单** → 改了什么、重点测什么、已知风险
3. **原型设计** → 交互流程必须走通

没有 PRD 就没有 QA——提醒用户先完成 PM 阶段。

---

## 规则

### 规则 1：自动化前置
`bash scripts/test.sh` 必须全部通过才继续。
脚本失败 = 代码有基本问题，不需要往下测。

### 规则 2：PRD 验收标准 100% 覆盖
PRD 中的每一条验收标准，都必须有对应的验证动作和结果。
- 不允许跳过任何一条
- 不允许写"同上"或"同上通过"
- 必须写明：验证方式（怎么测的）+ 结果（通过/未通过）

### 规则 3：必须用浏览器验证
代码审查不能替代浏览器测试。
用 Playwright MCP 打开页面，模拟真实用户操作。
PRD 中的每个交互流程，都必须在浏览器中走一遍。

Playwright 不可用时降级为：API 验证 + 代码追踪。
降级时必须在报告中标注哪些项"建议用户手动验证"。

### 规则 4：数据流必须闭环验证
凡涉及数据的改动（新增/修改/删除），必须验证完整链路：
- 写入 → 能否成功存入
- 读回 → 能否正确显示
- 持久化 → 刷新/重登后是否还在
- 降级 → 写入失败时是否静默丢数据
- 兼容性 → 旧数据是否导致新逻辑报错

### 规则 5：回归不能少
本次改动不能破坏已有功能。
对照 PRD 的"影响范围"，逐项验证受影响的功能是否正常。

### 规则 6：边界条件必须覆盖
每个功能的边界条件（PRD 中列出的），都必须验证：
- 空状态（无数据时）
- 未授权（未登录时）
- 异常输入（极端值、特殊字符）
- 网络异常（API 失败时的降级表现）

## 输出：测试报告

```
## 测试报告

### 自动化检查
- test.sh：✅ X/Y 通过

### PRD 验收标准逐项
| # | 验收标准 | 验证方式 | 结果 |
|---|---------|---------|------|
| 1 | ... | 浏览器/代码/API | ✅/❌ |

### 交互流程走查（来自 PRD 原型）
- 流程1：✅/❌
- 流程2：✅/❌

### 数据流验证（如适用）
- 写入/读回/持久化/降级/兼容性

### 回归测试（来自 Dev 交接的影响范围）
- 功能A：✅/❌

### 边界条件（来自 PRD）
- 场景1：✅/❌

### 结论
- X/Y 通过
- 是否允许推送：是/否
- 建议用户手动验证：是/否（列出项）
```

## 硬性红线
- **全部通过才允许推送**
- **禁止仅凭自动化脚本判定通过**
- **禁止未经浏览器验证就标记通过**
- **没有 PRD 就不做 QA——先回 PM 阶段**
