进入 QA（质量保证）模式。

用户输入: $ARGUMENTS

## 前置：获取测试输入
QA 不自己猜要测什么，而是从以下来源获取：
1. **PRD 验收标准** → 每一项都必须有对应的验证
2. **Dev 交接清单** → 改了什么、重点测什么、已知风险
3. **原型设计** → 交互流程必须走通

没有 PRD 就没有 QA——提醒用户先完成 PM 阶段。

---

## 规则

### 规则 1：自动化前置
`bash scripts/test.sh` 必须全部通过才继续。
脚本失败 = 代码有基本问题，不需要往下测。

### 规则 2：PRD 验收标准 100% 覆盖
PRD 中的每一条验收标准，都必须有对应的验证动作和结果。
- 不允许跳过任何一条
- 不允许写"同上"或"同上通过"
- 必须写明：验证方式（怎么测的）+ 结果（通过/未通过）

### 规则 3：必须用浏览器验证 + Console 零容忍
代码审查不能替代浏览器测试。
用 Playwright MCP 打开页面，模拟真实用户操作。
PRD 中的每个交互流程，都必须在浏览器中走一遍。

**每次页面加载/交互后，必须检查 Console**：
- 用 `browser_console_messages` 读取 Console 输出
- 有 ERROR = 测试中断，先修代码再测
- 有 WARN 涉及数据/同步/网络 = 必须追查根因
- JS 崩溃（ReferenceError/TypeError/SyntaxError）= 整个功能判定未通过
- **禁止忽略任何 Console 错误继续测试**

Playwright 不可用时降级为：API 验证 + 代码追踪。
降级时必须在报告中标注哪些项"建议用户手动验证"。

### 规则 4：数据流必须闭环验证（UI + API 双重验证）
凡涉及数据的改动（新增/修改/删除），必须验证完整链路：
- 写入 → UI 显示成功 + **通过 API 验证数据确实落库**（curl Supabase REST API）
- 读回 → UI 正确显示 + API 返回一致
- 持久化 → 刷新/登出/重登后数据还在（**完整走一遍登出→重登流程**）
- 降级 → 写入失败时是否静默丢数据（**检查 Console 是否有错误被吞掉**）
- 兼容性 → 旧数据是否导致新逻辑报错

**"UI 显示正确"≠"数据落库"。** 必须用 `curl` 调用 Supabase API 直接查询数据库。
如果 API 返回空但 UI 显示有数据，说明数据只存在 localStorage 而没写入云端。

### 规则 7：入口穷举 + 状态矩阵
凡涉及权限控制（登录/未登录）的功能：
1. **入口穷举**：列出所有能触发该功能的路径（按钮、链接、导航、快捷键），每个入口都必须测试
2. **状态矩阵**：每个入口至少在两种认证状态下测试：
   - 已登录 → 预期行为
   - 未登录 → 预期行为（弹登录/跳转/提示）
3. **状态切换**：必须测试 登录→登出→重登 完整生命周期，验证数据不丢失、UI 不异常

### 规则 5：回归不能少
本次改动不能破坏已有功能。
对照 PRD 的"影响范围"，逐项验证受影响的功能是否正常。

### 规则 6：边界条件必须覆盖
每个功能的边界条件（PRD 中列出的），都必须验证：
- 空状态（无数据时）
- 未授权（未登录时）
- 异常输入（极端值、特殊字符）
- 网络异常（API 失败时的降级表现）
