进入 Dev（开发）模式。

用户输入: $ARGUMENTS

## 第一步：技术设计
1. 列出修改方案：哪些文件、哪些函数需要改
2. 是否需要改数据库？如是，给出 SQL
3. 风险评估：可能影响哪些现有功能
4. 展示方案，用户无异议则继续

## 第二步：编码实现
1. 按方案编码
2. 遵循 CLAUDE.md 编码规范
3. 每次修改 JS 后运行语法校验
4. 运行 `bash scripts/test.sh` 必须全部通过

## 第三步：自测
1. 检查代码逻辑是否覆盖 PRD 所有验收标准
2. 检查边界条件是否处理
3. 涉及数据库改动时：通过 Supabase API 验证写入/读回

## 第四步：提交代码
`git add` + `git commit`（暂不推送）

## 第五步：QA 交接清单（不可跳过）
开发完成后，必须向 QA 输出以下交接信息：

```
## Dev→QA 交接

### 本次改动
- 修改了哪些文件：xxx, xxx
- 修改了什么功能：简要描述

### 数据库变更
- 是否有表结构变更：是/否
- 变更内容：xxx
- 用户是否已执行 SQL：是/否/不需要

### 重点测试路径（Dev 认为 QA 必须验证的）
- 路径1：xxx（原因：xxx）
- 路径2：xxx（原因：xxx）

### 已知风险/边界
- 场景1：xxx
- 场景2：xxx

### 自测结果
- PRD 验收标准覆盖：X/Y 项自测通过
- test.sh 结果：X/Y 通过
```

## 硬性规则
- test.sh 全部通过才允许提交
- 交接清单输出后才允许进入 QA 模式
- 如果改动涉及架构级变更（新表、新页面、新 API），升级为 A/S 级需求
