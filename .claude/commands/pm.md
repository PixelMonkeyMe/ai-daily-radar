## 第一步：调研（不可跳过）
在写 PRD 之前，必须先完成调研：
1. **读现有代码**：检查与需求相关的现有实现，理解当前逻辑
   - 涉及前端？读 docs/fav.js 相关函数
   - 涉及后端？读 scripts/build_site.py 相关模板
   - 涉及数据库？检查 Supabase 表结构
2. **查历史需求**：查看 docs/changes/ 了解之前做过什么，避免重复"发现"已有需求
3. **查已知坑点**：读 CLAUDE.md 的"已知坑点"章节，避免踩同样的坑

## 第二步：需求分析
1. **理解核心目标**：不要急着写 PRD，先思考这个需求背后的 Why。用户真正想解决什么问题？
2. **主动提案**：分析当前需求是否是最优解，有没有更简单的方案能达到同样效果。如果有，向用户提出讨论。
3. **挑战需求**：如果发现与现有功能冲突、或有矛盾，主动指出。
4. **检查冲突**：基于调研结果，明确说明新需求与现有功能的交互关系

## 第三步：输出 PRD（必须包含以下章节）
- 背景与目标（Why）
- 现有功能分析（基于调研，说明当前状态和与新需求的关系）
- 备选方案对比（如有更优解）
- 功能要求（编号列表）
- 🖼 原型设计（文本线框图 + 交互流程图）
- 边界条件 & 异常场景
- 验收标准（每一项都可测试，用 yes/no 判断）
- 影响范围（列出会被修改的文件）
- 需求分级（S/A/B/C）

## 第四步：QA 评审 PRD
写完后用 QA 视角审视：
- 验收标准是否完整、可测试？
- 边界条件是否遗漏（空值、未登录、网络错误、旧数据）？
- 交互流程是否顺畅（用户操作路径无断点）？
- 与现有功能是否冲突？
补充建议后修订 PRD。

## 第五步：等待用户确认
**PRD 必须用户确认后才进入开发。**

## 原型设计格式
```
┌─────────────────────────────────┐
│  页面布局（文本线框图）           │
│  [组件] [按钮] [输入框]          │
└─────────────────────────────────┘

交互流程：
  用户操作 A → 系统响应 B → 用户操作 C → ...
```

## 需求分级标准
- S：新功能 / 架构变更 → 完整 ①→②→③→④
- A：现有功能改进 → ①→③→④
- B：Bug 修复 → ③→④
- C：配置/文案 → 直接改→验证
