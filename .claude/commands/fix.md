进入 Fix（Bug 快速修复）模式。

用户输入: $ARGUMENTS

## 第一步：复现 & 定位根因
1. 理解用户描述的现象和复现路径
2. 检查相关代码、线上文件、Console 报错、最近 git 变更
3. 确定根因

## 第二步：分析给用户确认
说明：
- 根因是什么
- 修复方案是什么
- 影响范围有多大
- **等待用户确认后才修改**

## 第三步：修复
1. 修改代码
2. 运行 `bash scripts/test.sh` 全部通过
3. 提交代码

## 第四步：推送 + 线上验证
1. git push
2. 等待部署完成
3. 线上冒烟测试（验证 bug 已修复 + 未引入新问题）
4. 用户确认修复

## 升级判断标准
以下情况必须升级为 A/S 级需求，走完整流程：
- 修改超过 3 个文件
- 涉及数据库表结构变更
- 涉及新增/修改 Edge Function
- 影响范围超出当前功能模块
- 修复方案与现有架构不兼容

## 回归范围
修复后必须验证：
- bug 本身已修复
- 直接关联功能正常（同页面、同数据流）
- 登录/登出/收藏/同步 核心路径正常（每次必测）

## 第五步：事件驱动复盘（不可跳过）
Bug 修复后，必须判断这个 bug 是 workflow 哪个环节漏掉的：

```
复盘判断：
1. 这个 bug 是什么类型？
   - 代码逻辑错误 → 可能是 Dev 自测不够 / QA 没测到
   - 需求遗漏 → 可能是 PM 没覆盖
   - 数据流问题 → 可能是 QA 数据流验证没做
   - 配置/环境问题 → 可能是已知坑点没记录

2. 对应环节是否有规则防止？
   - 有规则但没执行 → 执行问题，提醒下次注意
   - 没规则 → workflow 缺陷，需要补充规则

3. 需要修正 workflow 吗？
   - 是 → 直接修改对应的 .claude/commands/*.md 或 CLAUDE.md
   - 否 → 记录到 CLAUDE.md 的"已知坑点"
```

**复盘输出**：
- 如果修正了 workflow 文件：commit 并说明原因
- 如果只是新增坑点：更新 CLAUDE.md 已知坑点章节
- 告知用户复盘结论
